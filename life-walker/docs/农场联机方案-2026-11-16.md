# 农场联机方案（B 方案：开启服务器）· 2026-11-16

> 决策：走 `serverCloud` 服务端方案；好友通过 **玩家 ID 搜索 / 名字搜索 / 排行榜直接发请求** 建立。
> 目标：真实跨玩家农场——访问好友农场、浇水、偷菜、好友请求，全部由服务端校验。

## 一、为什么必须开服务端

| 能力 | clientCloud（单机模式） | serverCloud（联网模式） |
|---|---|---|
| 写自己的数据 | ✅ | ✅ |
| 读别人的数据 | ❌（只能通过排行榜附加字段偷看，且有分页/排名限制） | ✅ `serverCloud:Get(uid, key)` |
| 写别人的数据（偷菜/浇水） | ❌ | ✅ 服务端校验后写 |
| 防作弊 | ❌ 客户端说什么就是什么 | ✅ 服务端裁决 |

偷菜/浇水的本质是**修改别人存档**，只有服务端能做。

## 二、架构

```
客户端（现有单机玩法不动）
  ├─ 游戏本体：战斗 / 农场 / 好友 UI（沿用现有代码）
  ├─ FarmNet 客户端层：登录后拉自己文档、动作上行、事件下行、本地缓存
  └─ 大厅（引擎大厅 + 自定义入口）：开始游戏 = 创建单人房间（连服务器）

服务端（headless，只做数据服务，不跑战斗）
  ├─ FarmStore：农场文档 / 浇水 / 偷菜 / 收获 / 好友关系（纯逻辑，已实现）
  ├─ 持久化：serverCloud（按 uid 存文档）
  └─ 远程事件：water / steal / plant / harvest / friend_request / accept …
```

**关键取舍**：服务端**不参与战斗**，只持有农场数据。战斗仍然在客户端跑（现有代码零改动），
所以不会变成"重新写一遍游戏"，这也是这条路能在 1~2 周内做完的原因。

## 四、风险

1. **切 multiplayer 后启动流程变化**：必须先连服务器，离线不能玩；需要评估是否保留"本地游玩"分支。
2. **存档双写**：客户端本地存档与云端文档要有一致性策略（以云端为准 + 本地回退）。
3. **服务端成本**：每次访问好友农场都要读对方文档；已用 `FarmStore.Snapshot` 裁剪字段，避免把种子/果实等隐私字段下发。
4. **反作弊边界**：浇水/偷菜/收获全部服务端裁决；客户端只做预演与提示。
